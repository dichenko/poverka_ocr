# Проверка на Windows — 13 сентября 2026

Среда: Windows x64, CPython 3.11.14, PaddleOCR 3.7.0, PaddlePaddle 3.3.1 (CPU),
PaddleX 3.7.2. Зависимости установлены в `.venv`; совместимость установленных
69 пакетов подтверждена `uv pip check`. Полный набор версий в `requirements.txt`.

## Реальное распознавание

Использованы копии первых трёх фотографий из соседней папки `dataset`. JSON находятся
в `verification/output`, входные копии — в `verification/input`.

| Файл | Строк | Время повторного OCR |
|---|---:|---:|
| 001_photo_1786587901508.jpg | 10 | 3.26 с |
| 002_photo_1786588903555.jpg | 11 | 3.50 с |
| 003_photo_1786589767381.jpg | 15 | 4.31 с |
| blank.png — белое изображение | 0 | 0.36 с |
| broken.jpg — намеренно испорченный файл | 0, ImageReadError | <0.01 с |
| контроль.png — искусственный тест текста | 3 | 1.18 с |

Контрольное изображение создано Pillow, шрифт Arial, чёрный текст на белом фоне.
Реальная модель вернула строки без расхождений:

```text
СЧЁТЧИК ВОДЫ
ITELMA 00123456
№ A-123/45.67
```

Это проверка алфавита и работы конвейера, не оценка точности на фотографиях.
На реальных фото есть ошибки: например, в первом снимке модель вернула `00252`
для более длинной цифровой надписи. Такие строки намеренно оставлены без исправлений.
Размеченного эталона для расчёта CER/WER нет; метрика точности не заявляется.

## Автоматические проверки

- `python -m unittest -v test_main`: 6 тестов прошли. Проверены EXIF-поворот и BGR,
  все пять расширений, исключение вложенных папок, русское имя, NumPy/JSON,
  порядок текста и координаты, пустой результат, ошибки чтения/OCR,
  продолжение после ошибки, skip/overwrite и однократная загрузка модели.
- `python verify_outputs.py`: прошёл. Все 6 JSON прочитаны стандартным `json`;
  число строк, порядок, версия движка, диапазон confidence и границы координат проверены.
- Без `--overwrite`: 6 пропусков, код 0; содержимое и время изменения JSON не менялись.
- С `--overwrite`: 5 успехов, 1 ожидаемая ошибка испорченного JPEG, код 1;
  время изменения всех шести JSON обновилось. После ошибки следующий файл обработан.
- При обоих повторных запусках сетевой `socket.connect` в процессе OCR блокировался:
  модели загрузились из `models/official_models`, распознавание завершилось успешно.
- SHA-256 входной подборки до/после совпали; хеши трёх копий совпали с оригиналами.
- `python main.py` с пустой стандартной папкой `input`: корректное завершение без
  загрузки модели, код 0. Стандартные папки созданы автоматически.

Для повторной проверки используйте команды из README. Файлы `verification` являются
тестовыми; намеренно испорченный `broken.jpg` не относится к пользовательскому датасету.


## Доработка показаний: фактическая проверка

11 модульных тестов прошли. Число разрядов проверено на искусственных рядах из 7, 8 и 9 ячеек.
Проверены X при противоречивых цифрах, десятичная точка, отсутствие поля и независимость
ошибки чтения показаний от сырого OCR.

На пяти реальных снимках автоматически найдено по 8 ячеек.

| Фото | meter_reading.value | Ячеек | Полное время |
|---|---|---:|---:|
| 051 | `X0030.68X` | 8 | 13.83 с |
| 057 | `00289.X2X` | 8 | 22.74 с |
| 071 | `006XX.XXX` | 8 | 19.78 с |
| 073 | `0X614.XXX` | 8 | 12.40 с |
| 089 | `XX3XX.37X` | 8 | 15.15 с |

Все пять JSON валидны; расположение десятичной точки, число ячеек и соответствие
value/cells проверены программно. items/full_text совпали с исходным OCR. Хеши
тестовых копий совпадают с оригиналами. После запуска с --overwrite выполнен обычный
запуск: пять файлов пропущены. Три модели использованы из локального кэша.

Полностью прочитанных показаний на этой подборке нет: новый модуль сохраняет
позиции пропущенных цифр как X. Это консервативный прототип для механических
счётчиков с тремя красными дробными разрядами, а не универсальный обученный
детектор показаний. На иных конструкциях качество и оценку числа ячеек нужно
проверять отдельно; широкая метрика точности не заявляется.
